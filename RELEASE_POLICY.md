# Fortress Kernel and FortressOS distribution — licensing and release boundary

Effective for future official releases, once adopted. This is a publication and licensing policy, not a claim that the current experimental tree has already been separated, nor a commercial EULA or a security certification.

## Products

**Fortress Kernel** is the open-source foundation: first-party privileged kernel mechanisms (CPU entry and interrupts, address spaces, memory ownership, scheduling, process/domain substrate, capability and IPC primitives, mandatory enforcement and device-grant mediation), and the public kernel-facing ABI needed to build independent software. The intended license for this first-party public code is Apache-2.0. Release supporting source/build materials are separately reviewed and explicitly licensed. External components retain their own licenses.

**Fortress Graphics (working component name)** is an additional open-source foundation, licensed Apache-2.0 for first-party code where rights permit. Its scope includes the baseline user-mode compositor/window server, surface and buffer protocols, software rendering and composition, basic display/presentation and input-routing interfaces, public graphics SDK/API, baseline window decoration and the rendering abstractions needed by independently developed applications and desktop shells. Publish the implementation, interface definitions, build dependencies and relevant conformance tests as a separately buildable source artifact. It must have a usable reference path without proprietary rendering modules. Keep hardware-specific drivers, firmware, vendor libraries, advanced GPU/compute and vGPU components separately classified; their required license terms remain in force. Public interfaces must not become authorization bypasses: focus, clipboard, capture, protected surfaces, display ownership and buffer grants remain subject to mandatory kernel/service security policy. A minimal public reference shell or examples may accompany the graphics stack, without committing the entire branded desktop, settings, proprietary applications or enterprise extensions to publication. No claim of implemented graphics features, KDE compatibility, or import of KDE/Qt code; third-party licenses require separate review.

**FortressOS** is the complete operating-system distribution built above Fortress Kernel. Beyond the explicitly open kernel, ABI and baseline graphics stack, its system services, filesystems, drivers, policy administration, branded desktop shell, applications, installers, management and enterprise extensions are separately classified for publication. New first-party distribution code is not automatically open source merely because it uses the public kernel. Maintainers may publish selected components under Apache-2.0 or another explicit license, or distribute separately licensed proprietary components in binary form. The full distribution's source is not part of the public kernel release by default. Free-of-charge distribution and open-source licensing are different questions; proprietary components may be provided free of charge or commercially under their own terms. Commercial terms are established separately.

These are product and publication boundaries, not claims about the current runtime privilege of a directory. No licensing boundary may justify weakening kernel security enforcement, introducing ambient privilege or hiding a privileged dependency of the open kernel. The public kernel must be independently buildable from its published source and explicitly declared permitted dependencies; proprietary services use documented versioned interfaces.

## Existing publications and contributor rights

The existing public preview includes experimental non-kernel code. All previously granted Apache-2.0 rights remain in force for the code to which those grants apply. This policy does not retroactively relicense, revoke, restrict commercial redistribution, or require removal of existing copies or forks. The root LICENSE and NOTICE remain intact. A private future version does not withdraw the earlier public version. Preserve contributor copyright and attribution; maintainers may not relicense third-party contributions beyond rights actually granted. Contributions to the public Apache-2.0 code continue under its existing contribution policy.

## Future public releases

Use distinct artifact names and versions: `fortress-kernel-vX.Y.Z` for public kernel source and optionally its independently built binary; `fortress-graphics-vX.Y.Z` for the open baseline graphics source and optional binary; `fortressos-vX.Y.Z` for an independently licensed distribution release where authorized. A distribution may contain Apache-2.0 kernel and graphics binaries, other open-source software and proprietary binaries without imposing its proprietary terms on components licensed otherwise. Publish distribution notices and required corresponding source or other compliance materials for each applicable component. Do not publish proprietary source in this repository or attach it to public releases.

Release preparation occurs in a restricted environment. Export a reviewed allowlist of public paths into a public-only tree; do not mirror private Git history, branches, CI logs, build caches, source maps, debug symbols or unreviewed archives. Review each file and its dependency/license provenance (including generated code, embedded assets, firmware and vendored dependencies); a directory name or root LICENSE alone is not sufficient classification. Public interfaces, documentation and proof artifacts are published only when reviewed and expressly in scope. Unknown or mixed rights block publication until resolved.

Every future release requires a per-artifact manifest with product, version, source identity, SHA-256, component-level SPDX license expressions (or a documented LicenseRef), copyright/attribution, dependency revisions, publication classification, applicable source availability and evidence of review. Include LICENSE, NOTICE where required, modification notices and third-party license materials. Verify public artifacts from their actual exported tree; a private-build PASS alone does not establish public-build reproducibility. Inspect archives and Git history for non-public content before pushing or tagging. Proprietary artifacts must be produced and distributed through separately authorized release channels. No automatic publication from the development repository.

Apache-2.0 permits proprietary use and redistribution subject to its terms, including Section 4. It does not remove obligations of other licenses. Copyleft components (including GPL, LGPL and MPL software) require component- and integration-specific review; merely placing code in a separate directory or service does not resolve all obligations. Do not relicense third-party code as Apache-2.0 without authority. Commercial terms must not override users' rights under applicable open-source licenses. Review rights, provenance and license compliance before any release, and consult qualified counsel for commercial contracts or uncertain combinations.
