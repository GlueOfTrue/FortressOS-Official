# Fortress Kernel and FortressOS distribution — licensing and release boundary

Effective for future official releases, once adopted. This is a publication and licensing policy, not a claim that the current experimental tree has already been separated, nor a commercial EULA or a security certification.

## Products

**Fortress Kernel** is the open-source foundation: first-party privileged kernel mechanisms (CPU entry and interrupts, address spaces, memory ownership, scheduling, process/domain substrate, capability and IPC primitives, mandatory enforcement and device-grant mediation), and the public kernel-facing ABI needed to build independent software. The intended license for this first-party public code is Apache-2.0. The open kernel product includes all first-party modules that are architecturally part of its baseline kernel, including hybrid-kernel subsystems or loadable modules; static versus dynamic linkage, directory placement and protection-domain placement do not by themselves create a separate licensing product. Kernel-internal dependencies needed for the open baseline must not be withheld. Standalone system services using the public ABI are not automatically kernel modules. Specialized, independently developed optional modules for specific deployment profiles may be distributed under distinct licenses, including proprietary terms where rights permit. A supplied kernel and its selected modules form one versioned, integrated runtime and assurance subject, not independently certified products or a fork of the common kernel. This does not withdraw Apache-2.0 rights from any existing code or make a mandatory dependency of the public baseline proprietary. The source of the common kernel, including its baseline modules and security fixes, remains public. An optional module that must execute in the privileged kernel is explicitly part of that configuration's TCB; use isolated services wherever adequate. Each supported combination has a signed build/profile manifest, pinned module revisions and compatible interfaces, independent integration and adversarial evidence, and fail-closed behavior when required modules or hardware are absent. No arbitrary privileged module loading, hidden baseline dependency, or commercial entitlement in the kernel authorization path. Release supporting source/build materials are separately reviewed and explicitly licensed. External components retain their own licenses.

**Fortress Graphics (working component name)** is an additional open-source foundation, licensed Apache-2.0 for first-party code where rights permit. Its scope includes the baseline user-mode compositor/window server, surface and buffer protocols, software rendering and composition, basic display/presentation and input-routing interfaces, public graphics SDK/API, baseline window decoration and the rendering abstractions needed by independently developed applications and desktop shells. Publish the implementation, interface definitions, build dependencies and relevant conformance tests as a separately buildable source artifact. It must have a usable reference path without proprietary rendering modules. Keep hardware-specific drivers, firmware, vendor libraries, advanced GPU/compute and vGPU components separately classified; their required license terms remain in force. Public interfaces must not become authorization bypasses: focus, clipboard, capture, protected surfaces, display ownership and buffer grants remain subject to mandatory kernel/service security policy. A minimal public reference shell or examples may accompany the graphics stack, without committing the entire branded desktop, settings, proprietary applications or enterprise extensions to publication. No claim of implemented graphics features, KDE compatibility, or import of KDE/Qt code; third-party licenses require separate review.

**FortressOS** is the complete operating-system distribution built above Fortress Kernel. Beyond the explicitly open kernel, ABI and baseline graphics stack, its system services, filesystems, drivers, policy administration, branded desktop shell, applications, installers, management and enterprise extensions are separately classified for publication. New first-party distribution code is not automatically open source merely because it uses the public kernel. Maintainers may publish selected components under Apache-2.0 or another explicit license, or distribute separately licensed proprietary components in binary form. The full distribution's source is not part of the public kernel release by default. Free-of-charge distribution and open-source licensing are different questions; proprietary components may be provided free of charge or commercially under their own terms. Commercial terms are established separately.

These are product and publication boundaries, not claims about the current runtime privilege of a directory. No licensing boundary may justify weakening kernel security enforcement, introducing ambient privilege or hiding a privileged dependency of the open kernel. The public kernel must be independently buildable from its published source and explicitly declared permitted dependencies; proprietary services use documented versioned interfaces.

## Security and assurance editions

The common open kernel and open graphics foundation serve multiple separately licensed deployment profiles, rather than artificially splitting a microkernel from its own hybrid-kernel modules. The free baseline is a usable, maintained and secure-by-design system: fundamental memory and process isolation, capability checks, mandatory-policy enforcement, basic integrity and confidentiality controls, ordinary encryption and trustworthy updates must not be paywalled or deliberately weakened. All first-party source belonging to the open kernel remains Apache-2.0 across the supported baseline, including security fixes.

Enhanced and high-assurance FortressOS editions may be commercially licensed and may include separately developed proprietary system services, security policy profiles, advanced information-flow and DLP workflows, independently protected audit, separation of duties, domain key management, attestation, specialized isolation, continuity and regulated-deployment integration, subject to component rights and security review. These are examples of possible future features, not a fixed edition matrix or existing capabilities. Keep the underlying mandatory enforcement and fail-closed semantics in the common kernel; a commercial entitlement does not mint security authority, disable baseline protections or silently downgrade a configured security profile. Do not use DRM or payment checks as a trusted kernel security decision.

Distinguish feature profile, threat model, assurance evidence and legal certification. A paid edition may include audited/certified configurations, scoped evidence, qualified releases, lifecycle maintenance and support only as actually available and authorized. A certificate, proof or test result applies only to its evaluated version, configuration and assumptions. No certification or specific regulatory eligibility is claimed. Closed source by itself is not a security mechanism; authorized assessors may need confidential source, build and proof access. Public release obligations for previously open code and third-party licenses remain unchanged.

### Maximum edition: mission-critical computing platform

The maximum commercial profile is intended to deliver measurable operational capabilities beyond stricter access policy. Deployment-specific modules are composable: not every secure workstation needs a cluster or banking peripherals. Basic virtualization, ordinary recovery, baseline protections and normal administration remain available in the free base. Proposed premium families (not implementation or licensing commitments for any particular third-party code):

- Advanced virtualization and isolation: hardware-backed VM boundaries, controlled device assignment, tenant-separated storage/network and CPU placement, confidential VMs (SEV-SNP/TDX only on verified supported platforms), attested key release, specialized virtual GPU allocation, VDI and cluster orchestration. Ordinary VMs must not be advertised as confidential.
- Mission-critical single-node resilience: protected resource reserves across CPU, RAM, IPC, process slots, storage and audit; watchdogs and supervised fault domains; restart with new authority generations; admitted latency/deadline contracts; transaction-aware recovery; hardware RAS integration and verified failover where hardware supports it. Essential baseline forward progress and ordinary recovery are not paid safety fixes.
- Multi-node continuity: replicated services and durable state, fenced failover, quorum/witness mechanisms, split-brain prevention, idempotency and durable transaction deduplication, planned maintenance and migration where state/device semantics permit, geographically separate disaster recovery, tested backups and restore. Differentiate HA, fault tolerance and disaster recovery; no blanket zero-loss or zero-downtime guarantee.
- Banking, payment and industrial profiles: HSM integration, non-exportable keys, independent per-device authorization, dual control and split knowledge, authenticated and replay-resistant transactions, controlled peripheral I/O, auditable reconciliation and offline recovery. Exactly-once effects only within explicitly proven transaction boundaries and cooperating systems.
- High-assurance information protection: compartment/label and egress workflows, protected audit witnesses, anti-rollback policy state, independent key domains, immutable evaluated deployment manifests, offline signed updates, qualified long-term maintenance, confidential assessor access and specialized hardware integration.
- Advanced operations: capacity-aware resource admission, reserved service classes, coordinated update/recovery, compliance evidence export and operator separation. Publish measured SLOs, relevant RTO/RPO, fault-injection results and accepted hardware/firmware matrix before making commercial guarantees.

Keep licensing and feature profiles distinct from runtime security policy and evaluated assurance levels. Existing entitled installations do not lose functionality or downgrade on expiry; feature-update rights, security maintenance within the announced support lifecycle and support/SLA are separate terms. No mandatory online licensing or kernel DRM. Maximum-edition engineering does not expand the current baseline milestone.

## Existing publications and contributor rights

The existing public preview includes experimental non-kernel code. All previously granted Apache-2.0 rights remain in force for the code to which those grants apply. This policy does not retroactively relicense, revoke, restrict commercial redistribution, or require removal of existing copies or forks. The root LICENSE and NOTICE remain intact. A private future version does not withdraw the earlier public version. Preserve contributor copyright and attribution; maintainers may not relicense third-party contributions beyond rights actually granted. Contributions to the public Apache-2.0 code continue under its existing contribution policy.

## Future public releases

Use distinct artifact names and versions: `fortress-kernel-vX.Y.Z` for public kernel source and optionally its independently built binary; `fortress-graphics-vX.Y.Z` for the open baseline graphics source and optional binary; `fortressos-vX.Y.Z` for an independently licensed distribution release where authorized. A distribution may contain Apache-2.0 kernel and graphics binaries, other open-source software and proprietary binaries without imposing its proprietary terms on components licensed otherwise. Publish distribution notices and required corresponding source or other compliance materials for each applicable component. Do not publish proprietary source in this repository or attach it to public releases.

Release preparation occurs in a restricted environment. Export a reviewed allowlist of public paths into a public-only tree; do not mirror private Git history, branches, CI logs, build caches, source maps, debug symbols or unreviewed archives. Review each file and its dependency/license provenance (including generated code, embedded assets, firmware and vendored dependencies); a directory name or root LICENSE alone is not sufficient classification. Public interfaces, documentation and proof artifacts are published only when reviewed and expressly in scope. Unknown or mixed rights block publication until resolved.

Every future release requires a per-artifact manifest with product, version, source identity, SHA-256, component-level SPDX license expressions (or a documented LicenseRef), copyright/attribution, dependency revisions, publication classification, applicable source availability and evidence of review. Include LICENSE, NOTICE where required, modification notices and third-party license materials. Verify public artifacts from their actual exported tree; a private-build PASS alone does not establish public-build reproducibility. Inspect archives and Git history for non-public content before pushing or tagging. Proprietary artifacts must be produced and distributed through separately authorized release channels. No automatic publication from the development repository.

Apache-2.0 permits proprietary use and redistribution subject to its terms, including Section 4. It does not remove obligations of other licenses. Copyleft components (including GPL, LGPL and MPL software) require component- and integration-specific review; merely placing code in a separate directory or service does not resolve all obligations. Do not relicense third-party code as Apache-2.0 without authority. Commercial terms must not override users' rights under applicable open-source licenses. Review rights, provenance and license compliance before any release, and consult qualified counsel for commercial contracts or uncertain combinations.
